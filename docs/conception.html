1. Contexte, objectifs et périmètre

Le suivi des cotisations versées par les parents est actuellement tenu dans un classeur Google Sheets (un onglet par année scolaire : 23-24, 24-25, 25-26, 26-27). Le projet consiste à remplacer ce classeur par une application web professionnelle offrant un CRUD complet, un tableau de suivi consolidé identique au classeur, la génération de documents PDF (reçus de paiement, rapport annuel) et leur envoi automatique par email.

1.1 Objectifs

  • Centraliser et fiabiliser les données : parents, enfants, paiements, frais d’envoi et de retrait (barème MVola), par année scolaire.
  • Supprimer les formules manuelles : totaux, reste à collecter et statistiques calculés automatiquement.
  • Produire des reçus PDF propres pour chaque paiement et un rapport annuel imprimable.
  • Envoyer le PDF au parent par email en un clic, avec journal d'envoi (traçabilité).
  • Conserver l'historique des années scolaires passées (équivalent des onglets 23-24 … 26-27).
  • Importer les données existantes du classeur pour ne rien perdre (cf. annexe B).

1.2 Périmètre

1.4 Hypothèses de travail

  • Les montants sont exprimés en Ariary (Ar), sans décimales à l'affichage.
  • Le « Total » annuel (ex. 7 173 808 Ar pour 26-27) est un montant cible fixe, saisi une fois par année scolaire — confirmé par le client.
  • La colonne « Transferts » = frais d'envoi (transfert à distance) + frais de retrait d'après le barème de l'opérateur (affiche MVola), arrondis au millier supérieur (ex. 6 572 → 7 000).
  • Une ligne du classeur ≈ un parent ; les noms d'enfants (séparés par des virgules) deviennent des entités individuelles.
  • Les localités entre parenthèses (F/tsoa, A/be, Toliara, Tanà, Tuléar, V/marina) correspondent à des villes rattachées au parent.

3.2 User stories principales

  • US1 — En tant que gestionnaire, je sélectionne l'année scolaire active (26-27) et tout l'écran s'y filtre, comme les onglets du classeur.
  • US2 — Je crée un parent avec sa ville et l'email de réception, puis j'ajoute ses enfants (un ou plusieurs).
  • US3 — J'enregistre un paiement : dès la saisie du montant, les frais d'envoi + retrait sont calculés automatiquement d'après le barème MVola et arrondis au millier supérieur (modifiables si besoin) ; le tableau, les totaux et le reste se mettent à jour instantanément.
  • US4 — Je génère le reçu PDF d'un paiement, je le télécharge ou l'envoie par email au parent en un clic.
  • US5 — J'exporte le rapport annuel PDF (tout le tableau + totaux) et je l'envoie par email à la direction.
  • US6 — Je consulte l'historique des emails envoyés (destinataire, date, statut succès/échec) et je renvoie en cas d'échec.
  • US7 — J'archive une année terminée et je crée la nouvelle ; les données restent consultables.

3.3 Règles de gestion

Réf.Règle
RG1Un paiement appartient à un seul parent et à une seule année scolaire ; un parent peut effectuer plusieurs versements.
RG2Total de l'année = montant cible fixe saisi une fois par année scolaire (ex. 7 173 808 Ar pour 26-27) — champ annees_scolaires.total_cible, modifiable dans les Paramètres.
RG3Encaissé = Σ paiements.montant ; Transferts = Σ paiements.frais_total (par année).
RG4Reste = Total cible fixe − (Sommes + Transferts) — mêmes termes que la formule client, en valeur positive : 7 173 808 − (6 930 000 + 171 000) = 72 808 Ar. Affiché en rouge tant qu’il est positif ; en vert si ≤ 0 (objectif atteint).
RG5Un parent ayant des paiements ne peut pas être supprimé (suppression refusée → archivage) ; un parent sans paiement est supprimé avec ses enfants (cascade).
RG6Chaque paiement peut produire un reçu PDF numéroté (format REC-2627-0042) ; toute tentative d'envoi email est journalisée avec son statut.
RG7Les montants sont positifs ; le montant d'un paiement ne peut pas être négatif (contrainte base).
RG8Une seule année scolaire est « active » à la fois dans l'interface ; les autres restent consultables en lecture.
RG9Transfert d'un paiement = frais d'envoi (transfert à distance) + frais de retrait, lus dans bareme_frais selon la tranche du montant (barème opérateur, ex. MVola — annexe C). Le dépôt est gratuit (0 Ar).
RG10Arrondi : la somme (envoi + retrait) est arrondie au millier supérieur : frais_total = ceil((envoi+retrait)/1000)×1000 — ex. 6 572 → 7 000 Ar. Le pas (1 000) et le mode (supérieur) sont paramétrables.
RG11Auto / manuel : dès que l'utilisateur saisit le montant (« Sommes »), le champ Transfert se pré-remplit (RG9 + RG10) ; il reste modifiable — toute saisie manuelle est tracée (frais_auto = false).

4. Architecture générale de la solution

Architecture 3 tiers classique, découplée par une API REST : le frontend React ne parle jamais directement à la base de données ; toute opération passe par l'API Express, qui concentre la logique métier, la génération PDF et l'envoi email.

5. Conception de la base de données (PostgreSQL)

5.1 Schéma SQL (DDL)

-- Base : cotisations_db — PostgreSQL 16
CREATE TABLE annees_scolaires (
    id            SERIAL        PRIMARY KEY,
    libelle       VARCHAR(7)    NOT NULL UNIQUE,           -- « 26-27 »
    date_debut    DATE          NOT NULL,
    date_fin      DATE          NOT NULL,
    total_cible   NUMERIC(12,2) NOT NULL DEFAULT 0,        -- montant cible FIXE de l'année (RG2, ex. 7 173 808)
    statut        VARCHAR(10)   NOT NULL DEFAULT 'active', -- active | archivee
    cree_le       TIMESTAMPTZ   NOT NULL DEFAULT now()
);

CREATE TABLE parents (
    id           SERIAL      PRIMARY KEY,
    nom_complet  VARCHAR(120) NOT NULL,
    telephone    VARCHAR(30),
    email        VARCHAR(160),                    -- requis pour l'envoi du reçu PDF
    ville        VARCHAR(60),                     -- Fianarantsoa, Antsirabe, Toliara, Tananarive…
    adresse      TEXT,
    cree_le      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE enfants (
    id               SERIAL       PRIMARY KEY,
    parent_id        INT          NOT NULL REFERENCES parents(id) ON DELETE CASCADE,
    nom_complet      VARCHAR(120) NOT NULL,
    date_naissance   DATE,
    cree_le          TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_enfants_parent ON enfants(parent_id);

CREATE TABLE paiements (
    id              SERIAL        PRIMARY KEY,
    parent_id       INT           NOT NULL REFERENCES parents(id)         ON DELETE RESTRICT,
    annee_id        INT           NOT NULL REFERENCES annees_scolaires(id) ON DELETE RESTRICT,
    montant         NUMERIC(12,2) NOT NULL CHECK (montant > 0),        -- « Sommes » (RG7)
    frais_envoi     NUMERIC(12,2) NOT NULL DEFAULT 0,   -- frais d'envoi barème (RG9)
    frais_retrait   NUMERIC(12,2) NOT NULL DEFAULT 0,   -- frais de retrait barème (RG9)
    frais_total     NUMERIC(12,2) NOT NULL DEFAULT 0,   -- colonne « Transferts » (RG10 : arrondi)
    frais_auto      BOOLEAN       NOT NULL DEFAULT TRUE, -- false si saisi manuellement (RG11)
    CHECK (frais_envoi >= 0 AND frais_retrait >= 0 AND frais_total >= 0),
    mode_paiement   VARCHAR(20)   NOT NULL DEFAULT 'especes'
                    CHECK (mode_paiement IN ('especes','mvola','orange_money',
                           'airtel_money','virement','autre')),
    reference       VARCHAR(60),
    date_paiement   DATE          NOT NULL DEFAULT CURRENT_DATE,
    note            TEXT,
    cree_le         TIMESTAMPTZ   NOT NULL DEFAULT now()
);
CREATE INDEX idx_paiements_annee  ON paiements(annee_id);
CREATE INDEX idx_paiements_parent ON paiements(parent_id);

CREATE TABLE bareme_frais (                            -- barème opérateur (MVola — annexe C)
    id           SERIAL        PRIMARY KEY,
    operateur    VARCHAR(20)   NOT NULL DEFAULT 'mvola', -- mvola | orange | airtel | autre
    type_frais   VARCHAR(10)   NOT NULL,                 -- envoi | retrait
    tranche_min  NUMERIC(12,2) NOT NULL,                 -- ex. 250 001
    tranche_max  NUMERIC(12,2) NOT NULL,                 -- ex. 500 000
    frais        NUMERIC(12,2) NOT NULL,                 -- ex. 1 900 (envoi) / 3 400 (retrait)
    UNIQUE (operateur, type_frais, tranche_min)
);

CREATE TABLE emails_logs (
    id             SERIAL       PRIMARY KEY,
    paiement_id    INT          REFERENCES paiements(id) ON DELETE SET NULL,
    parent_id      INT          REFERENCES parents(id)   ON DELETE SET NULL,
    destinataire   VARCHAR(160) NOT NULL,
    type_document  VARCHAR(20)  NOT NULL,               -- recu | rapport
    sujet          VARCHAR(200) NOT NULL,
    statut         VARCHAR(10)  NOT NULL,               -- envoye | echec
    erreur         TEXT,
    envoye_le      TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE utilisateurs (                            -- optionnel (M9, phase 2)
    id            SERIAL       PRIMARY KEY,
    nom           VARCHAR(120) NOT NULL,
    email         VARCHAR(160) NOT NULL UNIQUE,
    mot_de_passe  VARCHAR(100) NOT NULL,               -- hash bcrypt
    role          VARCHAR(20)  NOT NULL DEFAULT 'agent', -- admin | agent
    cree_le       TIMESTAMPTZ  NOT NULL DEFAULT now()
);

5.2 Vue « tableau consolidé » — le cœur applicatif

Cette vue reproduit exactement le classeur : une ligne par parent, la liste de ses enfants, les sommes et transferts cumulés pour l'année choisie. Les totaux et le reste (RG3, RG4) sont calculés par l'API à partir de cette vue.

CREATE VIEW v_tableau_annuel AS
SELECT a.id    AS annee_id,
       p.id    AS parent_id,
       p.nom_complet AS parent,
       COALESCE(string_agg(e.nom_complet, ', ' ORDER BY e.nom_complet), '—') AS enfants,
       COALESCE(SUM(pa.montant), 0)          AS sommes,
       COALESCE(SUM(pa.frais_total), 0)      AS transferts
FROM       annees_scolaires a
CROSS JOIN parents p
LEFT JOIN  enfants  e  ON e.parent_id = p.id
LEFT JOIN  paiements pa ON pa.parent_id = p.id AND pa.annee_id = a.id
GROUP BY a.id, p.id, p.nom_complet;

6. Conception de l'API REST (Express)

6.1 Conventions

  • Base URL : /api/v1 (versionnée) · format JSON UTF-8 sauf endpoints PDF (flux binaire).
  • Enveloppe de réponse : { "success": true, "message": "…", "data": …, "meta": { page, total } } ; erreur : { "success": false, "error": { code, message, details } }.
  • Pagination : ?page=1&limit=25 · Recherche : ?search=liva · Filtre : ?annee_id=4.
  • Codes HTTP : 200 lecture · 201 création · 400 requête invalide · 404 introuvable · 409 conflit/doublon · 422 validation Zod · 500 erreur serveur.
  • Toute entrée est validée par un schéma Zod avant d'atteindre le contrôleur ; tout SQL est paramétré.

8.3 Flux de génération

  1. L'API charge les données consolidées (paiement + parent + enfants + année) via le service d'accès données.
  2. Le service PDF injecte ces données dans un gabarit HTML (templates/recu.html, styles inline, format A5 pour le reçu, A4 paysage pour le rapport).
  3. Puppeteer rend le gabarit en PDF (marges, en-têtes/pieds de page, numérotation) et renvoie un Buffer.
  4. Le buffer est soit streamé au navigateur (Content-Type: application/pdf, Content-Disposition: attachment), soit transmis au service email comme pièce jointe — le même gabarit sert aux deux usages.
Point de conception clé : le PDF est généré côté serveur uniquement, ce qui garantit des documents identiques quel que soit le navigateur et permet l'envoi par email sans intervention de l'utilisateur.

9. Module d'envoi d'emails (PDF joint)

9.1 Configuration SMTP

  • Nodemailer avec un transport SMTP configuré par variables d'environnement (annexe A) : Gmail avec mot de passe d'application (rapide à mettre en œuvre) ou Brevo/Mailgun (300+ emails/jour gratuits, recommandé en production).

// services/email.service.js — logique cible (extrait de conception)
async function envoyerRecu(paiementId) {
  const data = await repo.getPaiementComplet(paiementId);  // 3. données
  if (!data.parent.email) throw new AppError(422, 'Email du parent manquant');
  const pdf = await pdfService.genererRecu(data);          // 5-6. buffer PDF
  const info = await transporter.sendMail({                // 7. envoi
    from: process.env.MAIL_FROM,
    to: data.parent.email,
    subject: `Reçu de paiement ${data.numeroRecu} — Année ${data.annee}`,
    html: gabarits.emailRecu(data),
    attachments: [{ filename: `recu-${data.numeroRecu}.pdf`, content: pdf }],
  });
  await repo.journaliserEnvoi({ paiementId, destinataire: data.parent.email,
    statut: info.accepted.length ? 'envoye' : 'echec', erreur: null });
  return { message: 'Email envoyé au parent' };            // 10. réponse
}
